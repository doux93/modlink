# ModuLink Studio 产品路线与模块定位

## 产品定位

ModuLink Studio 是一个以设备会话为中心、基于手册和实测证据、带安全授权与复盘能力的模组调测工作台。

主闭环：

```text
设备会话 -> 型号/固件识别 -> 手册/实测证据 -> AI/诊断方案
         -> 安全授权 -> 执行 -> 记录复盘
```

后续功能应优先服务这个闭环。不能形成可复用证据、执行记录或项目资产的孤立工具页，不应继续扩张。

## 下一阶段产品化计划

### P1：项目与会话持久化

目标是让一次现场调测可以中断、恢复、交接和复盘，而不是关闭软件后只剩零散导出文件。

建议持久化的数据：

```text
projects
device_sessions
ai_conversations
ai_messages
executions
diagnostic_reports
stress_runs
attachments
evidence_snapshots
```

实施要点：

- 使用 SQLite 保存结构化数据，日志和大附件使用文件存储并在数据库中记录引用。
- 项目记录客户/设备、端口、识别型号、固件、SIM/网络环境和备注。
- 会话关联 AI 对话、诊断、压测、AT 执行及当时采用的知识与实测证据快照。
- 支持项目 ZIP 导出与导入，敏感字段默认脱敏。
- 数据库升级必须有 schema version 和迁移脚本。

验收标准：重启软件后能恢复项目、设备会话、AI 对话和执行历史；导出的项目可在另一台机器导入并复盘。

### P1：AI Markdown 与流式输出

目标是降低长回答等待时间，并让指令、表格、证据和执行确认清晰可读。

实施要点：

- AI 后端支持 SSE 或 HTTP chunk，Tauri 按 request ID 发送 delta、complete、error 事件。
- 前端逐段更新当前消息，切换页面后仍由会话状态接管，不依赖某个组件持续挂载。
- 停止生成必须真正取消后端请求，并忽略迟到事件。
- Markdown 使用安全渲染器，禁用原始 HTML 或进行严格清洗。
- 支持代码块、表格、引用、链接和代码复制；AT 指令块可进一步生成结构化提议。
- 工具调用、授权原因和执行确认继续使用结构化卡片，不能混进普通 Markdown 后再靠文本解析。

验收标准：首段可见延迟明显低于完整响应时间；可取消；快速连续提问不会串流；危险 HTML 不会执行；工具确认卡行为不退化。

### P2：知识包安装与更新

目标是把目前的开发目录选择升级为可交付、可验证、可升级和可回滚的知识产品。

建议使用 `.mlkb` ZIP 容器，至少包含 manifest、主题映射、命令目录、质量报告及正文文件。

实施要点：

- 安装前校验 schema、包 ID、版本、适用型号、文件哈希和可选数字签名。
- 解压时防止路径穿越、符号链接逃逸和超限压缩包。
- 包安装到版本化目录，同一包允许多版本共存。
- 先在临时目录完成验证，再原子激活；失败时保留当前版本。
- 支持查看版本、启用、停用、回滚和卸载；卸载前检查是否被项目证据快照引用。
- 第一阶段支持离线导入，第二阶段再增加在线仓库、更新检查和差分下载。

验收标准：损坏包和不兼容包不能激活；升级失败不影响旧版本；可一键回滚；切换型号后只启用适用包。

## 压测模块审计

### 定位结论

保留，但建议产品名称逐步调整为“稳定性验证”或“长稳测试”。它是主闭环中的验证阶段，不是一个孤立的串口循环发送器。

适用价值：

- 单条 AT 通道和查询指令的重复稳定性验证。
- MQTT、HTTP、FTP、注网等多步骤业务流程的长时间循环验证。
- 复现重连、网络抖动、偶发 URC、超时和资源泄漏类问题。
- 将失败步骤、延迟和恢复效果沉淀为可复盘证据。

### 当前完成度

| 部分 | 完成度 | 已有能力 | 主要缺口 |
|---|---:|---|---|
| 单指令压测 | 80% | 次数、间隔、超时、正则判定、失败停止、P95、失败样本、取消、HTML 报告 | 模板保存、历史对比、CSV/JSON 导出、阈值判定 |
| 场景压测引擎 | 75% | 复用诊断流程、按次数/时长运行、继续/停止/恢复策略、恢复指令、步骤延迟、失败聚类、趋势、取消 | 断线与设备重启后续跑、环境快照、基线比较 |
| 安全与主线集成 | 80% | 场景步骤和采集命令后端授权、未复核确认、硬限制不可绕过、统一执行记录 | 与项目、会话和知识证据快照的完整关联 |
| 产品体验 | 60% | 实时进度、趋势、结论、报告导出、流程就地编辑 | 压测模板、运行队列、历史仪表盘、跨版本对比 |

阶段性整体完成度约 70%。引擎已经可用，离正式长稳验证产品的距离主要在持久化、恢复和结果比较。

### 后续优先项

1. 压测结果纳入项目与会话持久化，记录设备/固件/知识包/配置快照。
2. 支持保存压测模板和从历史运行重新发起。
3. 增加基线阈值：成功率、P95、连续失败次数、恢复成功率，并自动给出通过/失败。
4. 增加串口断开、设备重启后的有限次数重连和续跑策略。
5. 增加 CSV/JSON 导出及同一模板的历史趋势比较。

## 示例与测试用例模块审计

### 定位结论

保留底层流程模型和执行引擎，但重新划分产品概念。手册自动转换出的“示例”不能直接宣称为“测试用例”。

建议统一到“验证中心”：

```text
验证中心
|- 推荐检查       官方内置、已复核的基础体检
|- 标准测试用例   有适用范围、前置条件、预期结果和实机验证记录
|- 手册示例       自动转换的参考流程，默认不可直接批量执行
`- 我的流程       用户创建、从日志生成或克隆修改的流程
```

AI、诊断执行和场景压测继续复用同一个 `DiagFlow` 引擎，但内容生命周期、展示标签和执行策略必须分开。

### 当前数据审计（2026-08-10）

`data/usecases` 当前包含：

- 212 条手册转换用例，共 994 个步骤，中位数 4 步，范围 2 至 18 步。
- 212 条全部为 `verified: false`，尚无一条正式实机复核用例。
- 152 条带适用范围，60 条 `applies_to` 为空。
- 169 条包含 URC 等待，18 条包含服务器地址等占位参数。
- 212 条均未显式声明 `execution_mode`，当前依赖运行时推断。
- 自动转换用例没有使用 retry 或补充 collect 能力，虽然执行引擎本身已经支持这些结构。
- 另有 1 条内置、已复核的推荐检查流程，共 9 个步骤。

### 当前完成度

| 部分 | 完成度 | 说明 |
|---|---:|---|
| 流程执行引擎 | 80% | 支持多命令步骤、解析、条件判定、URC、重试、补采集、可选步骤、取消和结构化报告 |
| 流程编辑体验 | 65% | 支持新建、克隆、编辑、删除、排序、基础判定和从串口日志导入，但未暴露引擎全部能力 |
| 手册示例自动转换 | 70% | 已能批量生成流程和部分型号范围、URC 判定，但仍有参数化和范围缺口 |
| 用例质量治理 | 25% | 当前 0/212 实机复核，缺少审核、版本、验证设备和固件等治理信息 |
| 整体产品完成度 | 55% | 已经是有用的参考流程库，但还不能作为正式测试资产库宣传 |

### 数据模型需要补齐

标准测试用例至少增加：

- `lifecycle`: `recommended | example | draft | reviewed | verified | deprecated`
- `parameters`: 参数名、类型、默认值、是否敏感和输入校验
- `preconditions`: SIM、注网、PDP、服务器、证书、接线和设备状态
- `expected`: 用例级通过条件和关键输出
- `execution_mode`: `readonly | mutating | unknown`，生成时显式落盘
- `verified_on`: 型号、固件、运营商、验证时间和设备标识脱敏值
- `author`、`reviewer`、`revision`、`source_topic_ids`

### 后续优先项

1. 先改展示和术语：将 212 条归入“手册示例”，不再与“标准测试用例”混称。
2. 对 `applies_to` 为空、含占位参数或 `execution_mode=unknown` 的示例禁止直接进入场景压测；必须先克隆为“我的流程”并补参数。
3. 扩展编辑器，支持参数、前置条件、URC、重试、补采集和执行影响范围。
4. 建立复核工作流，优先将网络注册、PDP、MQTT、HTTP、FTP 各整理 1 至 3 条标准基线用例。
5. 把实测通过结果与型号、固件、用例 revision 绑定；只有满足复核规则才允许标记为 verified。

## 推荐实施顺序

```text
1. 项目与会话持久化
2. AI Markdown 与流式输出
3. 验证中心术语和内容分层
4. 压测历史、模板与基线判定
5. 知识包安装、升级与回滚
6. 标准测试用例复核与持续扩充
```

项目持久化优先，是因为 AI、诊断、压测和知识证据都需要一个共同的归档载体；先解决归属关系，后续功能不会继续产生彼此割裂的历史数据。
